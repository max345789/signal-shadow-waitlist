# Architecture & Design Decisions (DECISIONS.md)

This file records every sensible default chosen when building **Trust Marketplace**, along with the rationale and constraints.

---

## Phase 0: Foundation

### 1. Project Location & Tooling
- **Decision**: Scaffolded in `trust-marketplace` using Next.js (App Router), TypeScript (`strict: true`, `noUncheckedIndexedAccess: true`), Tailwind CSS `3.4.19`, Radix UI primitives, Prisma `6.x` (PostgreSQL), `ioredis`, `jose`, `otpauth`, `zod`, Vitest, and Playwright.
- **Why**: Next.js + TypeScript + Tailwind + Radix UI + Prisma + Redis matches Section 7 defaults. Using Tailwind `3.4.19` with `theme.colors` completely replacing default colors ensures non-Section-4 colors (e.g., `purple-*`, `slate-*`, `emerald-*`) cannot even be generated by Tailwind CSS.

### 2. Strict Section 4 Color System & WCAG AA Contrast Rules
All UI surfaces, text, borders, icons, and focus outlines strictly use the 11 Section 4 solid hex colors. Zero gradients, zero neon, zero glow shadows, zero pastel fills.

Mathematical WCAG 2.1 contrast audit of Section 4 pairs revealed two critical rules enforced in code and verified by automated tests:

1. **Amber (`#B7791F`) is non-text UI only**:
   - `#B7791F` has contrast `3.64:1` on `White (#FFFFFF)`, `3.39:1` on `Cloud (#F5F7FA)`, `4.05:1` with `Ink (#1F2933)`, and `4.23:1` with `Deep Navy (#0B2545)`. None of those pairs meet `4.5:1` for normal text, though all exceed `3.0:1` (WCAG 1.4.11 non-text UI contrast).
   - **Rule**: Caution/Pending chips, alerts, and stage indicators render `White (#FFFFFF)` surface + `Ink (#1F2933)` text (`14.76:1`) + `Amber (#B7791F)` `1px` border and icon (`3.64:1`). Amber is never used as text foreground or behind text.
2. **Verified Green (`#1B7F5C`) cannot sit on Pale Blue (`#E8EEF6`)**:
   - `#1B7F5C` achieves `4.96:1` on `White (#FFFFFF)` and `4.62:1` on `Cloud (#F5F7FA)` (passes `4.5:1`), and `White` text on `#1B7F5C` achieves `4.96:1` (passes `4.5:1`). However, `#1B7F5C` on `Pale Blue (#E8EEF6)` drops to `4.25:1` (fails AA text).
   - **Rule**: Verified Green text/icons are paired exclusively with `White` or `Cloud` (or `White` on `Verified Green` background).

### 3. Max 3 Non-Neutral Colors Per View
- Neutrals: `Cloud (#F5F7FA)`, `White (#FFFFFF)`, `Ink (#1F2933)`, `Slate (#52606D)`, `Mist (#CBD2D9)`.
- Brand / Highlight / Semantic: `Deep Navy (#0B2545)`, `Trust Blue (#1E56A0)`, `Pale Blue (#E8EEF6)`, `Verified Green (#1B7F5C)`, `Amber (#B7791F)`, `Brick Red (#B42318)`.
- Product screens show at most 3 non-neutral colors simultaneously (typically `Deep Navy` + `Trust Blue` + one active semantic state). On `/style-guide`, a "Focused 3-Accent Mode" and "Full Component Matrix" toggle let reviewers verify both the 3-color rule and all component variants on one page.

### 4. Typography, Hero Numbers & Mobile Floor
- **Fonts**: `Inter` (UI & body) and `Source Serif 4` (headlines) loaded via `next/font/google` with reliable local fallbacks (`system-ui`, `Georgia`).
- **Scale**: Strictly `14px`, `16px`, `20px`, `28px`, `40px`.
- **Rule**: Body text is `>= 16px` (`text-16`) across mobile (`360px`) and desktop (`1280px`). `14px` (`text-14`) is reserved strictly for status chips, table/metric metadata, and form helper text. All financial metrics and stage indices enforce `font-variant-numeric: tabular-nums`.

### 5. Shape, Spacing, Motion & Focus States
- **Spacing**: Strict `8px` grid (`8px`, `16px`, `24px`, `32px`, `40px`, `48px`, `64px`).
- **Corner Radius**: `8px` across cards, inputs, buttons, and chips.
- **Elevation, Opacity & Borders**: `1px solid #CBD2D9` (Mist) borders instead of heavy shadows (`box-shadow: none`). Disabled controls (`bg-cloud text-slate border-mist`, `6.02:1` AA) and modal backdrops (solid `bg-deep-navy`) use 100% solid Section 4 colors rather than CSS `opacity` so colors never blend outside Section 4 or drop below WCAG AA contrast.
- **Required Form Indicators**: Required field markers use neutral `Slate (#52606D)` `(required)` text instead of `Brick Red`, reserving `Brick Red` strictly for errors and risk.
- **Tooltips / Disclosures on Touch & Desktop**: `InfoTooltip` supports click/tap toggle (for 360px touch devices), hover/focus, `Escape` dismissal, and `16px` readable copy clamped within mobile viewports.
- **Focus Ring**: `2px solid #1E56A0` (Trust Blue) outline with `2px` offset (`outline-offset: 2px`) on every interactive element, never glow/blur shadows.
- **Motion**: State-change transitions only (`150ms–250ms ease-out`, defaulting to `200ms`), disabled automatically under `@media (prefers-reduced-motion: reduce)`.

### 6. Authentication & Mandatory 2FA Gate
- **Decision**: Implemented a provider-agnostic auth boundary (`src/lib/auth/`) using `jose` (HS256 signed HTTP-only cookies), `node:crypto` (`scryptSync` + `timingSafeEqual`) for local credential verification, and `otpauth` (RFC 6238 TOTP) for 2FA.
- **Why**: Avoids writing custom cryptographic primitives while functioning without external Clerk/Auth0 keys in local development and CI. Ready to swap to Clerk/Auth0/OIDC via `AUTH_PROVIDER` in production.
- **Trust Invariant**: `canEnterDealRoom(session)` strictly denies access unless `session.twoFactorVerifiedAt` is a valid timestamp and the user holds an authorized role (`BUYER`, `SELLER`, `ADMIN`, `REVIEWER`). Login attempts are rate-limited in memory/Redis.

### 7. Database (PostgreSQL + Prisma) & Queues (Redis)
- **Decision**: `prisma/schema.prisma` targets PostgreSQL (`provider = "postgresql"`) and models all 19 core Section 8 entities (`User`, `Role`, `BuyerProfile`, `SellerProfile`, `Thesis`, `Business`, `BusinessMetric`, `Verification`, `Match`, `DealRoom`, `DealStage`, `Message`, `Document`, `DocumentView`, `Offer`, `ChecklistItem`, `EscrowTransaction`, `Notification`, `AuditLog`).
- **Local Development**: `docker-compose.yml` provides `postgres:16-alpine` and `redis:7-alpine`. When `DATABASE_URL` is absent in local Phase 0 smoke mode, auth falls back to an explicit, clearly labeled local development store (`AUTH_PROVIDER=local-dev`) rather than silently pretending to persist to Postgres.

### 8. Configurable Currency (Default `INR`)
- **Decision**: `src/lib/format/currency.ts` formats monetary figures using `Intl.NumberFormat` defaulting to `INR` (`en-IN`), with optional Indian compact shorthand (`L`, `Cr`) paired with full exact values and configurable support for `USD`, `EUR`, and `GBP`.

### 9. Verification & Testing in CI
- **CI**: `.github/workflows/ci.yml` runs `prisma validate`, `eslint`, `tsc --noEmit`, `vitest run`, `next build`, and Playwright responsive/accessibility verification.
- **Browser Testing**: Playwright targets installed system Chrome/Edge cleanly at `360x800` (mobile) and `1280x800` (desktop) to verify layout, zero horizontal overflow, visible keyboard focus, zero CSS gradients, and WCAG contrast.

## Phase 1: Listings and Vitals

### 10. Listing Schema Extensions & Q&A Persistence
- **Decision**: Extended `Business` in `prisma/schema.prisma` with `teaserSummary`, `founderStory`, `founderMediaType`, `techStack`, `financialSeriesJson`, `valuationLow`, `valuationHigh`, `valuationBasis`, `submittedAt`, `reviewedAt`, `reviewedById`, and `reviewerNote`, and added a dedicated `ListingQuestion` model for public buyer Q&A threads.
- **Why**: Supports all Section 5 & Section 6 Listing page elements (including financial charts, tech & assets, and Q&A) with normalized persistence and auditability.

### 11. Conservative Guided Valuation & Zero-Hype Framing
- **Decision**: Implemented `calculateGuidedValuation()` in `src/lib/domain/valuation.ts` using conservative sector profit multiples (`1.5x–4.0x` depending on sector, adjusted for weekly owner hours and annual growth rate, with a `0.8x–1.4x` pre-profit revenue fallback). Every output includes an explicit disclaimer that it is an illustrative estimate from seller-reported inputs, never a guaranteed exit price.
- **Why**: Aligns with Section 2 ("Never fake trust", "Never use urgency tricks or hype") and Section 3 ("guided valuation, auto-built listing").

### 12. Server-Side Redaction & Confidential Leak Guard
- **Decision**: `sanitizeListingForViewer()` in `src/lib/domain/listings.ts` strips `redactedName`, `redactedDomain`, `redactedCustomers`, and internal `reviewerNote`/`auditLogs` on the server unless the viewer is the owning Seller, an Admin/Reviewer, or a Buyer with a completed NDA. `detectConfidentialLeak()` scans all public copy (`teaserTitle`, `teaserSummary`, `reasonForSelling`, `financialNarrative`, `risksSummary`, `founderStory`) against distinctive brand tokens and domain labels, blocking submission and Admin approval if leaks exist. Saving an `APPROVED` or `PENDING_REVIEW` listing with `submitForReview: false` transitions it cleanly to `DRAFT` so unchecked edits never bypass review.
- **Why**: Enforces Section 6 ("Sensitive details (name, domain, customer names) are redacted until NDA is signed") at the data-serialization boundary rather than relying on client-only CSS hiding.

### 13. Strict Separation of Verified vs Seller-Reported Vitals & Honest Q&A Attribution
- **Decision**: Seller-created listings in Phase 1 create `BusinessMetric` rows strictly with `source = SELLER_REPORTED` and `verificationId = null`; API endpoints ignore any client-supplied verification fields and preserve existing connector-verified metrics/quarterly series on edits. The Listing detail page separates **Verified connected metrics** (`Verified Green`, active `Verification` record + source + `Last verified` timestamp) from **Seller-reported metrics (unverified)** (neutral `Cloud`/`Mist` panel + `Seller-reported` chip) and withholds green verified iconography when zero verified records exist. Buyer Q&A threads label unverified buyers honestly as `Prospective Buyer` (never `Verified Buyer` without an active KYC verification record) and block listing owners from posting buyer questions on their own listings.
- **Why**: Satisfies Section 2, Section 6, and Phase 1 acceptance criteria without faking trust.

### 14. Status-Tabbed Seller & Admin Views for the 3-Color Rule
- **Decision**: `/seller` and `/admin/review` organize listings into Radix Tabs by status (`Drafts & pending` / `Pending review`, `Approved`, `Flagged & rejected`). Admin review decisions (`APPROVE`, `FLAG`, `REJECT`) require a minimum 5-character reviewer note and append an `AuditLog` entry.
- **Why**: Prevents mixing `Amber`, `Verified Green`, and `Brick Red` chips on a single screen, maintaining Section 4's limit of `<= 3` non-neutral colors visible per view alongside `Deep Navy` and `Trust Blue`.

### 15. Local Founder Voice Note Media Endpoint
- **Decision**: Added `/api/media/sample-founder-note` returning a deterministic PCM WAV audio stream for sample listings and restricted `founderMediaUrl` to `https://` or `/api/media/` paths via `sanitizeFounderMediaUrl()`.
- **Why**: Avoids broken external media URLs, console 404 errors, and `javascript:`/`http:` URL risks while keeping the Section 6 `<audio controls>` founder voice note functional offline and in CI.

## Phase 2: Buyer Thesis and Matching

### 16. Weighted Match Scoring Engine & Cross-Currency Normalization
- **Decision**: Implemented `scoreListingAgainstThesis()` and `rankListingsForThesis()` in `src/lib/domain/matching.ts` using normalized weights across active structured criteria (`sector: 22`, `askingPrice: 20`, `revenue: 15`, `minProfit: 15`, `ownerHours: 10`, `geography: 8`) plus free-text soft criteria (`10` alongside hard criteria, or `100` when free-text only). Cross-currency comparisons normalize via deterministic reference INR FX rates (`USD=84`, `EUR=91`, `GBP=107`) until live FX feeds are added.
- **Why**: Satisfies Section 6 ("weighted fit on hard criteria ... plus soft criteria from free text") without distorting scores when optional bounds are omitted. Partial proximity credit produces sensible rankings while **never hiding mismatches** (`mismatches` explicitly documents every ceiling overage, shortfall, sector/geography difference, missing connector requirement, and Seller-reported status).

### 17. Redaction-Safe Scoring & Free-Text Verification Guard
- **Decision**: `scoreListingAgainstThesis()` operates exclusively on `SanitizedListingView` public fields (never reading `redactedName`, `redactedDomain`, or `redactedCustomers`). Verification keywords in free text (`verified`, `stripe`, `razorpay`, `ga4`, `plausible`) earn credit ONLY when `metric.trust.isVerified === true` from an active non-expired `Verification` record; otherwise a mismatch is surfaced explicitly.
- **Why**: Prevents NDA-redacted details from leaking through rankings or alert notifications and prevents expired or Seller-reported metrics from earning free-text trust credit.

### 18. Saved-Thesis Feed, Instant Preview, and Alert Threshold (`>= 70`)
- **Decision**: Wired Home's `"What do you want to buy?"` prompt (`HomeThesisForm`) from the Phase 0 `/style-guide?thesisPrompt=` stub to `/thesis/new?prompt=...` with deterministic prompt hint extraction (`extractThesisHintsFromPrompt()`). Anonymous users can preview ranked matches immediately (`POST /api/matches/preview`) without signing in, while saving theses (`POST /api/theses`), viewing saved-thesis feeds (`/` and `/matches`), and receiving alerts require a `BUYER` (or `ADMIN`) account. Admin listing approvals (`reviewListingAsAdmin` -> `APPROVED`) automatically evaluate `alertsEnabled: true` theses via `evaluateAndSendThesisAlertsForListing()`, creating a `Notification` when `score >= 70` (and respecting explicit target `sector` unless overall fit `>= 85`) and recording `alertSentAt` on `(thesisId, businessId)` so re-approvals never duplicate alerts.
- **Why**: Lets prospective buyers evaluate the marketplace immediately before sign-in while enforcing strict per-buyer ownership on saved `Thesis`, `Match`, and `Notification` records.

### 19. Expanded Sample Seed Catalog & Responsive 3-Business Compare Grid
- **Decision**: Added two additional `APPROVED` sample listings (`sample-biz-media-04` Content & Media at ₹48 L and `sample-biz-mkt-05` Marketplace at ₹88 L) and one `Sample data`-labelled thesis (`sample-thesis-01`) for `sample-buyer-01`, keeping existing indices `[0..2]` unchanged. `/compare` caps selection strictly at `<= 3` businesses on both client and server (`GET /api/compare`) and renders each dimension in a responsive `grid-cols-1 md:grid-cols-3` comparison layout.
- **Why**: Provides 4 distinct approved sample listings across different sectors, budgets, and workloads so three distinct buyer theses produce three distinct top-ranked results out of the box, while avoiding wide `<table>` horizontal overflow at `360px` mobile width.

### 20. Anonymized Seller Demand Summary & Strict Trust-Color Isolation
- **Decision**: `/seller` computes aggregate Phase 2 buyer-thesis match counts (`>= 70` fit) and top score per approved listing (`getBuyerDemandSummaryForSellerListings()`) without exposing buyer identities or private thesis criteria. Across `MatchResultCard`, `HomeSavedThesesFeed`, `MatchesClient`, `ThesisBuilderClient`, and `CompareClient`, `Verified Green` renders exclusively for real active verification records (never for high fit scores, match reasons, or alert toggles), and mixed-trust comparisons keep `<= 3` non-neutral colors by using neutral-bordered status chips with explicit labels (`Verification expired`, `Connection failed`) when `Verified Green` is already present.
- **Why**: Keeps `Verified Green` strictly tied to active third-party verification records and enforces Section 4's `<= 3` non-neutral colors rule across every interactive state.

## Phase 3: Verification and Connectors

### 21. Regulated Identity (KYC) & Proof of Funds Flows Without Raw Document Storage
- **Decision**: Implemented `/verify` (`VerificationCentreClient`) and `/api/verification/identity` + `/api/verification/proof-of-funds` using regulated provider adapters (`Persona` / `Digio KYC` for Identity, `Setu AA` / `Plaid Assets` for Proof of Funds). Submissions enter `PENDING` with masked references (`****482F`), sync `BuyerProfile.identityStatus`, `BuyerProfile.proofOfFundsStatus`, and `SellerProfile.identityStatus` in PostgreSQL, and require Admin/Reviewer verification in `/admin/review` (`POST /api/admin/verifications/[id]/review`) before earning `VERIFIED` status (90-day TTL for KYC, 30-day TTL for Proof of Funds).
- **Why**: Satisfies Section 2 ("Never fake trust", "Use proven providers; do not write custom crypto"), Section 6 (Buyer KYC + Proof of Funds gate before `Data access`, enforced via `hasActiveBuyerDataAccessVerification()`), and Section 10 without storing full government ID numbers or banking credentials.

### 22. Read-Only Payment & Analytics Connector Adapters & Secret Redaction
- **Decision**: Implemented `src/lib/verification/connectors.ts` supporting read-only payment (`Stripe`, `Razorpay` -> `REVENUE`, `CUSTOMERS`) and analytics (`GA4`, `Plausible` -> `TRAFFIC`) connections. Raw API tokens/grants are validated at sync time and never stored in `metadataJson` or returned in API responses (only masked `accountHint` values are persisted). Sandbox mode deterministically tests valid (`rk_sandbox_valid_*`), failing/revoked (`*fail*`, `*revoked*`, `*invalid*`), and expired (`*expired*`) credentials, while `ENABLE_LIVE_CONNECTORS="true"` enables read-only HTTPS `GET` balance transaction reads for live Stripe restricted keys (`rk_live_*`).
- **Why**: Allows both real read-only production integration and deterministic offline/CI testing of connection success, failure, and expiration without faking trust or risking fund/account mutations.

### 23. Automatic Expiry Reconciliation, Auto-Refresh & Immediate Verified-Mark Removal
- **Decision**: `reconcileExpiredVerifications()` and `autoRefreshDueConnectors()` (`POST /api/verification/refresh`, `POST /api/verification/connectors/[id]/sync`, plus 60s active polling on `/verify`) automatically transition expired `VERIFIED` records (`expiresAt <= now`) to `EXPIRED`, transition failing syncs to `FAILED`, revert `Business.financialSeriesJson` from `VERIFIED` back to `SELLER_REPORTED`, emit `Notification` + `AuditLog` entries, and strip the green `Verified` mark immediately across `ListingDetailClient`, `ListingCard`, `MatchResultCard`, `CompareClient`, and `addListingQuestion()` (`"Identity-verified Buyer"` reverts to `"Prospective Buyer"` on KYC expiry).
- **Why**: Guarantees Phase 3 acceptance ("connected metrics show a correct 'last verified' time and lose the mark when the connection fails or expires") without stale cache illusions.

### 24. Admin Verification Queue Integration & 3-Color Isolation
- **Decision**: Added a top-level `Verification queue` tab to `/admin/review` (`AdminReviewClient`) with status-grouped sub-tabs (`Pending checks`, `Verified`, `Expired, failed & revoked`) and enforced `<= 3` non-neutral colors across `VerificationCentreClient`, `MetricTile`, `ListingDetailClient`, and `AdminReviewClient` by falling back secondary mixed-trust chips to neutral `Mist`/`Cloud`/`Ink` styling with explicit status icons and labels when `Verified Green` or `Brick Red` is already active in the view.
- **Why**: Preserves backward compatibility with existing Phase 1/2 listing review flows while integrating Admin verification review and upholding Section 4's strict color-budget and accessibility rules.

## Phase 4: Deal Room

### 25. Mandatory 2FA + Participant RBAC & Deal Room Entry
- **Decision**: Implemented `/deals`, `/deals/[id]`, and all `/api/deal-rooms/*` routes guarded on every read and write by `canEnterDealRoom()` (verifying participant ownership `buyerUserId`/`sellerUserId` or `ADMIN`/`REVIEWER` staff role plus `twoFactorEnabled === true` and `twoFactorVerifiedAt` within 12 hours). Unauthenticated requests return `401`; missing/expired 2FA or non-participant access returns `403`.
- **Why**: Enforces Section 7 ("mandatory 2FA for anyone entering a deal room") and Section 10 ("Role-based access checked on the server for every deal-room read and write").

### 26. Two-Sided NDA E-Signature, Legal Placeholder Framing & Cross-Surface Redaction Unlock
- **Decision**: Implemented `POST /api/deal-rooms/[id]/nda` and `POST /api/deal-rooms/[id]/purchase-agreement` using draft placeholder templates explicitly badged **`Needs legal review`** (Section 10). Confidential fields (`redactedName`, `redactedDomain`, `redactedCustomers`) remain strictly `null` / `"Redacted until NDA is signed"` for the Buyer on BOTH `/deals/[id]` and `/listings/[slug]` until both Buyer and Seller complete NDA e-signature (`ndaSignedAt` populated).
- **Why**: Satisfies Section 6, Section 10, and Phase 4 acceptance ("redacted fields stay hidden until NDA completion") without risking single-sided or client-only bypasses.

### 27. Private Object Storage Vault, Virus Scan on Upload, Watermarked Previews & Signed URLs
- **Decision**: Stored uploaded and executed agreement payloads in a private non-public directory (`DEAL_VAULT_DIR` or `os.tmpdir()/trust-marketplace-private-vault`) via `src/lib/deal-rooms/vault.ts`. Uploads run `scanDocumentContent()` (blocking EICAR test signatures, PE/ELF headers, forbidden executable extensions, and `<script` payloads as `INFECTED`), auto-increment `version` per `(title, category)`, and generate watermarked copies. Downloads require a 5-minute HS256 signed URL (`/api/deal-rooms/[id]/documents/[docId]/signed-url` -> `/download?token=...`) bound to `(dealRoomId, documentId, viewerId)` and record a `DocumentView` + `DOCUMENT_VIEWED` `AuditLog` entry on every preview/download.
- **Why**: Satisfies Section 7 ("private object storage with signed URLs, virus scan on upload, watermarked previews") and Section 10 ("Log document access") without exposing unauthenticated static files.

### 28. Enforced Stage Machine, Threaded Chat + Rate Limits, Offers, Sector Checklists & Immutable AuditLog
- **Decision**: Wired `StageTracker` (with `strictThreeColorBudget` preserving `<= 3` non-neutral colors across all stage and error states) to `validateStageTransition()`, requiring executed NDA + active Buyer KYC + Proof of Funds for `NDA -> DATA_ACCESS` and an accepted `Offer` for `OFFER -> DUE_DILIGENCE`. Added deferred SSE realtime updates (`/api/deal-rooms/[id]/events`) starting 1s post-hydration, rate-limited threaded chat (`Message.parentId`) and uploads (`checkRateLimit()`), structured offer/counter-offer state machine (`validateOfferAction()`), sector-tailored `DUE_DILIGENCE` checklist generation (`generateDueDiligenceChecklistForSector()`), and append-only `AuditLog` entries on every state change.
- **Why**: Meets all Phase 4 acceptance criteria while keeping Playwright `networkidle` deterministic and upholding Section 4's strict color and typography rules.

## Phase 5: Escrow and Transfer

### 29. Licensed Third-Party Escrow Adapter Without Platform Custody
- **Decision**: Implemented `src/lib/escrow/provider.ts` supporting regulated third-party escrow providers (`Escrow.com` for `INR/USD/EUR/GBP` and `Castler Escrow` for RBI-regulated `INR` domestic M&A) with explicit `platformHoldsFunds: false` invariants, deterministic sandbox workflows, and an optional live `Escrow.com` REST boundary (`ENABLE_LIVE_ESCROW="true"` + `ESCROW_COM_API_KEY` / `ESCROW_COM_EMAIL`). Escrow amounts and currencies are validated strictly against the Deal Room's accepted `Offer`.
- **Why**: Enforces Section 2 ("Money, identity and documents are the sensitive areas. Use proven providers; do not write custom crypto or hold funds") and Section 6 ("Use a licensed third-party escrow provider. The platform never holds funds").

### 30. Visual Escrow Statuses, Two-Sided 7-Category Transfer Checklist & Release Gate
- **Decision**: Added `POST /api/deal-rooms/[id]/escrow` (`INITIATE`, `FUND`, `START_REVIEW`, `RELEASE`, `DISPUTE`) and the `Escrow & transfer` workspace tab in `DealRoomClient` displaying a visual 4-state escrow status strip (`Funded`, `In review`, `Released`, `Disputed`). Transitioning `ESCROW -> TRANSFER` requires `FUNDED`/`IN_REVIEW`/`RELEASED` escrow and automatically creates all 7 Section 6 `TRANSFER` `ChecklistItem` categories (`Domain`, `Code repository`, `Cloud & hosting`, `Payment accounts`, `Social handles`, `Customer data`, `Vendor contracts`). Buyer escrow `RELEASE` is blocked on the server until all 7 transfer categories have both `buyerConfirmedAt` and `sellerConfirmedAt` (`status === "CONFIRMED"`), upon which `TRANSFER` completes and `DealRoom.status` transitions to `COMPLETED`.
- **Why**: Guarantees two-sided asset handover before disbursement and enables a complete sandbox `INTRO -> TRANSFER` deal lifecycle with zero manual database edits.

### 31. Dispute Flagging, Room Freeze & 2FA-Guarded Admin Dispute Queue
- **Decision**: Flagging a dispute (`action: "DISPUTE"`) freezes `EscrowTransaction.status` to `DISPUTED`, sets `DealRoom.status` to `DISPUTED`, marks the active `DealStage` `BLOCKED`, blocks checklist/stage/escrow mutations, and surfaces the case in `/admin/review` under `Dispute queue` (`GET /api/admin/disputes` & `POST /api/admin/disputes/[id]/resolve`). Resolution requires an `ADMIN`/`REVIEWER` role with active 2FA (`canReviewAdminQueue` + `canEnterDealRoom`) and supports `RESUME_TO_IN_REVIEW`, `RELEASE_TO_SELLER`, and `REFUND_TO_BUYER`, writing `DISPUTE_RESOLVED` to `AuditLog` and notifying both parties. Under `DISPUTED` state, `DealRoomClient` and `AdminReviewClient` isolate `Brick Red` as the single semantic accent alongside `Deep Navy` and `Trust Blue` (suppressing `Verified Green`) to uphold Section 4's `<= 3` non-neutral colors rule.
- **Why**: Satisfies Section 4, Section 6, and Section 10 ("Provide clear reporting and dispute paths", "Role-based access checked on the server for every deal-room read and write").
